## Executive summary

**What the product is.** CaseGraph is a PayPal dispute investigation workspace.
It syncs authoritative dispute state, stores evidence as immutable revisions,
has a model build a provenance-typed graph of claims/facts/inferences/gaps, runs
a deterministic safety policy over that graph, and then requires a human to
approve an exact typed PayPal payload before any write. Ambiguous write outcomes
are never retried automatically.

**The concept is genuinely differentiated, though less novel than it first
appeared.** The commercial chargeback market (Chargeflow, Justt, Disputifier,
Stripe Smart Disputes, Chargebacks911) sells automated representment at volume on
card networks, and the most-cited weakness across those products is the
auditability of what the AI submitted and why. PayPal itself does not ship an AI
evidence builder. Recent research (FinRCA-Bench, 2026) independently supports the
provenance-first thesis: *which evidence the system can reach* dominates model
capability, and "a correct root-cause label is a weak proxy for an auditable one".
A later literature sweep (doc 11) found that the *mechanism* — provenance-gated
action execution with evidence-before-effect and approval bound to the exact
action — is published prior art (Agent-Sentry, Janus, PROVISO). CaseGraph's
defensible delta is the domain-specific enforcement: a byte-exact typed evidence
contract, risk/contradiction/missing-evidence policy semantics, and PayPal
`UNKNOWN_OUTCOME` reconciliation discipline. Position accordingly; do not claim
mechanism novelty.

**The execution did not match the concept.** Three defects made the shipped
product's flagship paths non-functional, and none of them were visible from the
test suite or the README:

1. `POST /actions/approve` and `POST /actions/{uid}/execute` were declared with
   unannotated parameters, so FastAPI parsed their JSON bodies as *query*
   parameters. **Every approval from the browser returned 422.** The entire
   human-approval → execution flow was dead over HTTP.
2. The reconciliation module referenced ORM columns, response fields and enum
   members that do not exist, so **any attempt to resolve an `UNKNOWN_OUTCOME`
   action raised `TypeError`** — the case stayed permanently blocked from further
   PayPal writes. The crown-jewel safety story had no working escape hatch.
3. The test suite called `drop_all` against `.data/casegraph.db`, the same file
   the running application used: **a `pytest` run could delete the developer's
   cases.**

**What changed.** All three are fixed and covered by tests that exercise the real
paths (HTTP through ASGI, reconciliation through the database). Beyond repairs,
the product is now demonstrable with zero credentials via a clearly-labelled
simulated PayPal transport plus a deterministic reference reasoner, and the
workspace was rebuilt from a single dense file into a componentised UI with a
real graph canvas, human-readable safety findings, and a typed action composer.

**Validation.** 133 tests pass, 0 fail (was 84 pass / 3 fail / 30 error in the same
sandbox, largely environmental). Frontend typecheck and production build pass.
The full journey — sync → intake → analyse → safety → approve → execute →
reconcile — was executed against a running server and against the simulator.

**What is still missing is not code.** No real PayPal sandbox run, no live model
run, no PostgreSQL/Redis/OIDC/ClamAV/OTel proof, no browser visual QA, no demo
video, and no open-source license file — and the rules make the last two blocking.
